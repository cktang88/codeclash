# Pushfront

Pushfront is an all-day war fought with your pushes. You sign in with GitHub and join a room (public, or private by invite). Every push you make to a public repository is read, sorted into what kind of code it is, and becomes a **platoon** that marches out of your capital against your neighbours. The capitals stand on a ring around an impassable lake or massif, and every army fights only the two armies beside it: take a neighbour's capital and its gates muster for you, and your army grows. The war is won when one player holds the whole ring. **No manual control: your code is your only command.** Nobody steers the armies, not even their players: each army's war council leads it, and you push real work and watch. Each room's war lasts a day, from one reset hour to the next (a new room's first war runs to the next reset, or to the one after if that is less than an hour away). At the room's reset hour (or as soon as one player holds every capital) the war ends and a **digest** is written; a fresh map begins at the reset.

This file is the source of truth for the rules and the architecture.

## 1. From a push to a platoon

### What we read

For every member, the server polls `GET /users/{login}/events/public` with an ETag, no more often than once a minute (or GitHub's `X-Poll-Interval`, if longer). An unchanged feed answers `304`, which costs no rate limit. A busy feed is read up to 3 pages of 100 events deep; a member's first poll looks back 24 hours. The poller wakes every 5 seconds and polls only as many members as keep it within 60% of the remaining rate limit until the limit resets (at least one while more than 50 requests remain). Events whose actor is another account (a renamed login taken by someone else) are skipped.

For each new `PushEvent` to a branch (keyed by `{repo}@{head}`), it calls `GET /repos/{o}/{r}/compare/{before}...{head}` once. A new branch (`before` is all zeros) falls back to `GET /repos/{o}/{r}/commits/{head}`. A branch deletion or a tag is skipped. A push that keeps failing is skipped after 5 tries; failures from GitHub's rate limit do not use up its tries.

- **Own commits only.** A commit is the member's when GitHub links its author to the member's account id; with no linked account, the author login is compared instead. Merge commits never count.
- **Mixed pushes.** When the range holds anyone else's commits or any merge (a `git pull`, an upstream sync), only the member's own commits are measured, one by one through `GET /commits/{sha}`, the newest 20 at most.
- **Once per commit.** A commit SHA already counted for that member is never counted again, whichever path (poller, webhook, another branch) brings it.

GitHub delivers public events anywhere from 30 seconds to several hours late. A member who wants near-real-time armies can add a repository webhook (push events) pointing at their personal hook URL. The server verifies the HMAC signature, ignores private repositories and pushes the member did not make, allows 20 deliveries a minute per hook, and then runs the same ingestion. Webhooks are strict: a commit with no GitHub-linked author does not count.

Only public repositories are read. Pushfront rewards real code: how much of it, how many files it touches, how complex it is, and what it is for (fixing a bug, shipping a feature, refactoring). The army grows in proportion to the real code: twice the work, twice the army, up to a daily cap. Generated and vendored code count for nothing, and the ledger's filters (duplicates, filler, shapes, canonical keys) keep padding from passing for work.

### Sorting lines into categories

Each changed file is classified by path. The first matching rule wins:

| Category | Matched by |
| --- | --- |
| vendor | `node_modules/`, `vendor/`, `third_party/`, `extern/`, `bower_components/`, `Godeps/`, `Carthage/`, `*.min.js`, `*.min.css` |
| generated | lockfiles, `dist/`, `build/`, `out/`, `target/`, `.next/`, `coverage/`, `__snapshots__/`, `*.map`, `*.pb.go`, `*_pb2.py`, `*.g.dart`, `*_generated.*`, `*.gen.*`, `*.snap`; any file whose first 5 lines say `@generated`, `DO NOT EDIT`, `auto-generated` or `Code generated by`; minified source (JS, TS, CSS or HTML additions averaging over 110 characters a line) |
| docs | `*.md`, `*.mdx`, `*.rst`, `*.adoc`, `*.txt`, `*.tex`, `*.bib`, `docs/`, `README`, `CHANGELOG`, `LICENSE`, `CONTRIBUTING` |
| test | `*.test.*`, `*.spec.*`, `__tests__/`, `test/`, `tests/`, `spec/`, `e2e/`, `*_test.go`, `test_*.py`, `*_test.py`, `conftest.py`, `src/test/`, `*Test.java`, `*Tests.swift`, `*_spec.rb`, `testdata/`, `fixtures/` |
| config | `.github/`, `Dockerfile`, `Makefile`, `*.yml`, `*.yaml`, `*.toml`, `*.ini`, `*.json`, `*.tf`, `*.nix`, `.gitignore`, `.editorconfig`, dotfiles |
| source | everything else with a known source extension |

Files of any other type (images, binaries, data) are ignored.

Inside **source** files, every *added* line from the patch is counted as one of these:

- **code**
- **comment**: a line comment, or a line inside a block comment, using the file's language syntax
- **blank**: whitespace only

Deleted source lines are counted as **removed**. Test, docs, config, generated and vendor files count added non-blank lines. When GitHub omits a patch because it is too large, the file's `additions` count is used, and those lines are all treated as code.

Every line then passes through the player's ledger (see *How many soldiers* below and [docs/fair-play.md](docs/fair-play.md)), which credits each distinct line once, leaves filler out, and caps code at 8000 lines per UTC day.

The nine line counts are `code, test, comment, docs, config, removed, generated, vendor, blank`. **Blank lines raise nothing.** They are recorded for the digest.

Two more numbers come from the source files:

- **Files touched:** source files where at least one code line carries a net change today. Test, docs, config, generated and vendored files don't count. The count is kept per UTC day, so a file touched yesterday counts again when it is changed today, and a file whose changes are all undone stops counting.
- **Complexity:** `branches + 3 × functions + ½ × names`, read from syntax trees (tree-sitter, `rules/complexity.ts`) for JavaScript, TypeScript and TSX, Python, Go, Rust, Java, Kotlin and Ruby:
  - **Branch points** are decision points: `if`, loops, case and match arms (not `default:` or `_ =>`), `catch`/`except`/`rescue`, ternaries, `&&` and `||` (`and`, `or`, `elif`, `unless`, `until`, `when`, Python comprehension clauses and the modifier forms in Ruby). A constant condition (`if (true)`, `while (1)`) decides nothing, and keywords inside strings and comments or identifiers named `case` or `if` are not syntax. Each code line is parsed on its own, set in the smallest code that completes it (`} else if (x) {` inside an `if`, `case 1:` inside a `switch`), so a line's count is a function of its text, exactly as its ledger key is. A line carries at most 2.
  - **Functions** are new functions, methods, classes and lambdas that lie wholly on added lines of one hunk, with at least 3 statement lines in their bodies that are credited as new code (statements in a nested function that counts itself are not its parent's). Stubs, one-liners and wrappers that only forward a call have fewer and earn nothing. Each is worth 3 points, carried by three of its newly credited lines (its first line, when that is new, and two statements); if any of the three is later deleted, the function is undone.
  - **Links** are new imports of this repository's own modules (relative paths in JavaScript and TypeScript, relative imports in Python, `crate::`, `super::` and `self::` in Rust, `require_relative` in Ruby, Go paths with `internal` or the file's own top directory, Java and Kotlin packages spelled by the file's own directories), never packages or the standard library. An import scores half a point for each imported name the file's added code uses (calls, member access, JSX tags, types; the members used through a namespace import), at most 3 points, and each module counts once a day per player. Names that appear only in comments or strings, unused imports and re-exports score nothing.
  - Hunks are fragments: each hunk's new side (added lines and their context) is parsed as one, relying on tree-sitter's error recovery, and only definitions and imports whose lines are all added count. Nothing outside the diff is fetched. Undercounting is preferred to overcounting.
  - Other languages, files that fail to parse, and lines too long to parse alone fall back to the keyword count (as above, per language family), with no functions or links. CSS, HTML and SQL have none. A push parses at most 1 MB of text (hunks and lines together, counted whether or not a line was parsed before, so a push measures the same in any process), and a file at most 250 ms, before falling back. When GitHub omits a patch, branch points are estimated as additions ÷ 12.

### The difficulty bonus: editing established code

Credit is linear in new lines, so without help a greenfield repository outearns a hard five-line fix in a big, much-worked file. The **difficulty bonus** pays extra code credit for *modified* lines: lines of other people's code that the push removes and replaces in the same file (`rules/difficulty.ts`). Pure additions are never multiplied.

**The multiplier.** Each file gets `M = clamp(1 + 0.8·s(LT/500) + 0.6·s((A−1)/4) + 0.4·s(age/365) + 0.4·s(C/50), 1, 4)`, with `s(x) = min(1, log2(1 + x))`, from its blame and history at the diff's base commit:

| Signal | What it is |
| --- | --- |
| LT | the file's lines before the change, not counting lines blamed to the pusher |
| A | distinct earlier authors other than the pusher (accounts at least 30 days old where GitHub says) |
| age | median age in days of the exact lines changed (removed lines; for a pure insertion, the context lines beside it), the pusher's own lines left out |
| C | the file's commits, the pusher's left out: how central it is |

Each signal saturates (500 lines, 5 authors, a year, 50 commits), so M reaches at most **3.2** (the clamp at 4 never binds with these weights). The vite-like fixture's `css.ts` (3,688 lines, 127 authors, lines from 2021, 519 commits) is ×3.2; a 212-line utility with 9 authors and lines from 2025 is ×2.6.

**The credit.** A file's extra credit is `f(modified) × (M − 1)` lines, where `f(n) = n` up to 40 and `40 + √(n − 40)` beyond, so a file's first 40 modified lines pay in full and a sweeping rewrite of one file pays little more. It is code credit: it joins the code term of the budget and goes through the knee and the cap with the code lines (`effectiveLedger`), and the line bonus is at most **2,000 lines a UTC day** (`DAILY_BONUS_CAP`). Files and complexity stay with the real lines; veteran ranks count the bonus as code (their file thresholds still need real files).

**The effort credit.** Lines are a poor measure of a hard fix in a big file: a maintainer's day of small, careful edits is a fraction of a greenfield day's lines, and a multiplier on those lines cannot close that gap. So each established file of others' code that the player **meaningfully modifies** in a UTC day (at least `MEANINGFUL_LINES` = 3 modified lines, by the same pairing as below, so whitespace, comment-only and one's own changes never qualify) also earns a fixed credit of `FILE_CREDIT × (M − 1) / (M_max − 1)` lines, where `M_max` = 3.2: the hardest file earns the full `FILE_CREDIT` (120 lines), an easy one little, and a file the repository gate holds to ×1.5 about a fifth. The day's effort credit is held to `FILE_CAP` (15) files' worth. It is folded into the bonus, so it is code credit through the knee and the cap. With it, the bonus is held to `BONUS_PER_CODE` = 43 × the day's code lines (the line bonus is at most 2.2 a line, the effort credit at most 120 per 3 lines), so a tiny day cannot explode.

**Repeat targets.** A file that held effort credit at the close of either of the two previous UTC days earns it again today only with at least `EFFORT_REPEAT_LINES` (10) modified lines instead of 3 (`EFFORT_REPEAT_DAYS` = 3): token edits to the same core file pay once in three days, while a maintainer's real work on the files they return to pays every day. The line bonus is not dampened. The rule reads only the file's state at the close of earlier days and its state today, so the credit is still awarded by the push that crosses the threshold and any split of the day adds up to its squash.

**Forks wait for the upstream.** In a fork (`fork` with a `parent`, from the repository's facts), edits of others' code pay plain code credit at push time: the multiplier counts as 1 and there is no effort credit. What the line bonus and the effort credit would have paid is computed then, from the push's own context and the file's frozen multiplier (whether a file is a fork's is frozen with it), and recorded with the push as pending (`server/upstream.ts`, table `upstream_pending`), with the diff's head, its own commits and its patch id (the changed lines without whitespace or line numbers, hashed). It pays only once the commits are in the upstream's default branch:

- `GET /repos/{parent}/compare/{default}...{head}` answers `behind` or `identical` (a merge commit or a fast-forward), or
- a pull request from the fork branch (`GET /repos/{parent}/pulls?state=closed&head=owner:branch`, once a day per branch) merged into the default branch holds **all** of the diff's commits (`GET /pulls/{n}/commits`; a rebase merge), or its merge commit has the diff's patch id (a squash of exactly that diff, merged after the push).

The first check runs right after the push's UTC day closes, then once a day; a diff not found within 14 days (`UPSTREAM_GIVE_UP_DAYS`) pays nothing. A webhook delivery of a merged `pull_request` only makes the member's rows for that repository due at once: the member signs their own deliveries, so the check always asks GitHub. Merged pull requests' commits and commits' patch ids are cached for good; the checks run every minute, at most 25 rows a run and 10% of the REST budget above a 2,000-request reserve. A day's reward is settled only after the day has closed, when its immediate bonus is final: `cap(immediate + found) − cap(immediate)` for the line bonus and the effort credit each, minus what was already credited for that day, so a fully merged fork day earns exactly what the same pushes would have earned in a repository of their own, each commit is credited once, and nothing is taken back. Past wars are closed, so the reward goes to the player's **current** war in each room as a one-off `upstream` input, `[tick, "upstream", p, repo, bonus, day]` (`day` is the UTC day of the pushes): bonus lines added to the war's ledger, not a push (it raises nothing until the player has pushed in that war, and it shares the knee, the cap and `BONUS_PER_CODE` with the rest of the bonus). At most one day's caps (`UPSTREAM_PER_DAY`, 3,800 lines) are credited to a player per UTC day; the rest waits for the next days, so pull requests banked and merged together cannot pour two weeks of bonus into one war. A replay never fetches anything: the reward is in its inputs.

**In the ledger.** Per file and UTC day (the same scope as *files touched*), the ledger keeps two tallies, both functions of the file's keys' net change today, counting each key once:

- *added*: code keys with a net addition today
- *removed*: code keys with a net removal today whose removed line someone else wrote, by the push's context; the mark is set when the key first goes negative and cleared when it comes back

The file's modified lines are the smaller of the two, its multiplier is **frozen at the first push that brings context for the file that day**, and its bonus and its effort credit are functions of (modified, multiplier): the credit is awarded by the push that takes the file to 3 modified lines and taken back exactly by a same-day revert that drops it below. So splitting a day's edits into pushes or squashing them earns exactly the same, even when a removal and its replacement arrive in separate pushes, and an edit undone the same day takes its bonus back exactly. Pairing is per file and day rather than per hunk: a hunk-level pairing cannot be squash-exact (a removal and its replacement can land in different pushes), and it would not stop anyone, since replacing others' lines in place is as easy as replacing them elsewhere. The pusher's own lines, today's or older, never count: blame names them, and lines added today cancel in the ledger before any context is consulted.

**Fetching the context** (`server/difficulty.ts`), before the push is recorded: in `ingestOnce`, between the compare and the store transaction, for the poller and the webhook alike.

1. The repository's facts over REST, once per repository per UTC day and revalidated with ETags: `GET /repos/{o}/{r}` (fork, source, `created_at`, stars, forks, size) and `/languages`. A repository with under 20 KB of code gets no context.
2. **One GraphQL query per diff**, at its base commit (the compare's merge base, or a commit's parent), with aliases for up to the **5 most changed source files that remove lines** (by `categorizePath`; never assets, lockfiles, vendored, generated or added files): `history(first: 100) { totalCount nodes { authoredDate author { user { databaseId createdAt } } } }` and `blame(path) { ranges { startingLine endingLine commit { … } } }`. Paths travel as variables. The old line numbers come from the patch's hunk headers (`@@ -a,b`). GraphQL needs a token; its rate-limit bucket is tracked apart from REST's (`x-ratelimit-resource: graphql`), and below 200 points left it is not used. Each query has a 2.5 s timeout.
3. If the batch fails or times out, one query per file (2 s each, in parallel).
4. For files still unread, the **local mirror** (`server/mirror.ts`), only when `MIRROR_DIR` is set and GitHub reports the repository at 50 MB or less: a bare partial clone holding commits and trees only, into which the blobs of each asked-for *source* file's own history are fetched in one batch, then `git blame --porcelain`. A mirror over 50 MB on disk is deleted; one untouched for 14 days is pruned. Git runs with no shell, a timeout per command, no prompts and no user config, on validated names. (A `--filter=blob:limit=256k` clone would have stored every small asset, lockfile and vendored file; fetching only source paths' blobs keeps the mirror to source, and a file over 256 KB is not blamed.) A mirror names people by commit email rather than account.
5. Otherwise the file has no context and its multiplier stays 1.

A mixed push measured commit by commit gets context for its newest 5 commits. The bonus is recorded in the push input, so a replay never fetches anything.

**Integrity.**

- Line ages are clamped to the repository's age (for a fork, its source's) and to the author account's age, so backdated history in a new repository reads as new.
- The pusher's account (and commit emails, for a mirror) are left out of authors, lines and ages.
- **The repository gate.** M is held to **×1.5** unless the repository (for a fork, its source) has at least 2 independent contributors with commits before today (accounts at least 30 days old) and at least 5 stars or 2 forks. Forks are not excluded (forking is how contributions happen), and a fork's blame is its own real history; a fork's bonus waits for the upstream (*Forks wait for the upstream*).

The preview shows each file's context: "Edited 2 lines of others' code in css.ts (3,688 lines, 127 authors, lines from 2021) ×3.2 → +4.4 lines of credit", with the gate's reason when it holds the multiplier, and the effort credit: "Fixed 3 hard files in vite (css.ts ×3.2, build.ts ×3.2, asset.ts ×3.2) → +359 lines of effort credit". A fork's commit shows "×3.2 pending upstream merge → … once merged".

**Purpose** comes from the first line of the newest counted commit's message. Conventional-commit prefixes come first, then common words. The first match wins:

| Purpose | Matched by |
| --- | --- |
| revert | `revert…`, "This reverts commit" |
| fix | `fix:`, `hotfix:`, `bugfix:`, or the words fix/fixes/fixed, bug, crash, regression, hotfix, patch |
| perf | `perf:`, or performance, optimize, faster, speed up |
| refactor | `refactor:`, or refactor, clean up, simplify, restructure, extract, remove, delete, dead code |
| chore | `chore:`, `ci:`, `build:`, `deps:`, `style:`, or bump, upgrade, dependencies, lockfile, release |
| feature | `feat:`, or add, implement, introduce, support, new, enable |
| work | anything else |

### How many soldiers: the day's ledger

An army is worth what its player contributed **today as a whole**, not push by push.

1. **The ledger.** Each player has a ledger for the day. Ingestion turns every push into signed changes to it: code, tests, comments, docs, config and removed lines; source files touched; branch points, function points and linked names; churn; filler. See [docs/fair-play.md](docs/fair-play.md) for how a diff is measured.
2. **The target army.** The ledger decides the army it is worth, `armyFor(ledger)`. Each push musters only the difference between that target and what the player has already raised.
3. **Splitting and squashing are equal.** Twenty small pushes and one squashed push of the same work leave the same ledger, so they raise an army of the same size and strength. Only the timing differs.
4. **Desertion.** When later pushes undo earlier work (deleting code added today, rewriting it back), the ledger shrinks and soldiers **desert**: the kinds furthest above their target first, and of each kind the waiting ones first, then the newest in the field. Soldiers never desert while the ledger is growing.
5. **Purpose follows the work.** The ledger also tallies code, removed lines and the difficulty bonus by purpose (a fix's bonus is fix work: it raises fix specialists as its code does). Undone lines come off the undoing push's own purpose first, then off the others in order, so the purposes always add up to the total: writing a feature and deleting it under a `fix:` message leaves nothing behind.

**The budget.** The army's size, in platoon slots, is **linear** in the day's contribution:

`floor((0.064·(code + bonus) + 0.14·files + 0.014·complexity + 0.008·removed) × (1 + 0.25 × conquered))`

(0 when there are no code or removed lines; computed in whole numbers as `BUDGET_PER_10K`), where *conquered* is how many capitals the player holds beyond its own home (see *Capture*), *code* is counted code lines, *bonus* the difficulty bonus for modified established code, line bonus and effort credit together (see *The difficulty bonus*; with code it goes through the knee and the cap, and is at most 43 × code), *files* source files touched, *complexity* `branches + function points + names ÷ 2` (see *Sorting lines*), and *removed* deleted lines the ledger had not credited to the player as their own recent work. Twice the real code raises about twice the army. Code is most of it; files and complexity season it, and removed lines count a little. A typical day (2000 code lines, 60 files, 570 points of complexity, 750 removed) is worth 150 slots, 128 of them from code; 100 lines raise about 6. Honest code carries about 1.42 points of complexity for every branch point the old keyword count found (this repository's last 81 commits: 7,994 points against 5,636 keyword branch points), so the complexity term weighs what the branch term did, and the thresholds once in branch points below are those times 1.42.

Each metric is first bounded by the real code behind it (`effectiveLedger`):

- **Code has a knee.** It counts in full up to 4000 lines a war (`CODE_KNEE`), at half value from there to 8000 (`CODE_CAP`), and not at all beyond: at most 6000 lines' worth (`credited`). The difficulty bonus shares the knee and the cap: `credited(code + bonus)`. Removed lines count up to 4000 a war, with no half-value stretch. With a linear budget the cap is what stops runaway volume. A knee rather than a cliff: a big honest day is not cut flat at one line, and padding toward the cap earns half. The ingestion cap (8000 a UTC day) matches, and the war's cap keeps a war that spans UTC midnight from counting two days.
- files at most `1 + code/20 + removed/100`
- function points at most `code/8` (one function per 24 lines; this repository has one per 32), so splitting code into many small functions pays only so far
- links at most a quarter of complexity, so branch points and functions always dominate
- complexity at most `code/2` (honest code here runs at about one point per three lines, the densest real commits at one per two)

Because the budget is a function of the day's ledger, many small pushes and one squashed push still raise exactly the same army.

**Specialists come out of the budget.** What the work was for, and how complex it was, spend up to 65% of the budget. They are paid in this order while the share lasts (`PAY_ORDER`): Dragon, Champion, Troll, Trebuchet, Griffin Rider, Bone Golem, Ballista, Paladin, Ranger, Wizard, Cleric, Knight, Outrider, Mercenary, Skeleton. Ballistae come before the other fixers, so a fixer's army always has its answer to the big; Clerics before Knights, so a small fix still raises its Clerics when its complexity asks for Knights too. Footmen fill the rest. The commit message therefore changes what the army is made of, never how big it is. Specialists counted per so many lines (Ballistae, Paladins, Rangers, Champions, Griffin Riders, Bone Golems, Trolls, Trebuchets) keep a steady share of the linear budget; those counted by a square root (Clerics, Outriders, Knights, Skeletons) take a smaller share of a bigger day, and Footmen make up the difference. All counts below are for the whole day:

| Raised by | Specialists |
| --- | --- |
| fix work *f* (fix code, plus the difficulty bonus earned by fixes: `fixWork`) | `2·floor(f / 180)` Ballistae, `2·floor(√f / 3.5)` Clerics, `2·floor(f / 350)` Paladins, `2·floor(f / 600)` Rangers: on a working day, about 40–45% of the fixers' slots are Ballistae |
| feature code *F* | `2·min(3, floor(F / 400), floor(files / 5))` Champions, less one for each Dragon |
| feature and plain work *W* | a Dragon at *W* ≥ 900 with files ≥ 10 and complexity ≥ 130; a second at 4000 / 40 / 570 |
| refactors | `2·floor(√(removed + code/2) / 1.5)` Outriders, from refactor lines; two Griffin Riders per 400 refactor lines removed (up to 6) |
| perf code *P* | `2·min(4, floor(√P / 3))` Wizards |
| reverts *R* (code and removed) | `2·floor(√R)` Skeletons; two Bone Golems per 600 lines (up to 4) |
| chore code *C* | `2·min(3, floor(√C / 2))` Mercenaries |
| complexity *X* | `2·floor(2·√(X/14))` Knights; with 200+ code lines, two Trolls per 215 points (up to 6) |
| files | two Trebuchets per 15 files (up to 6) |

Armies are twice the size they were when one slot was 0.032 a code line, and every count is twice what it was: each kind comes in pairs, and specialists are paid in pairs, so an army's make-up (the share each kind takes) is what it was. The Dragon is the exception: at most one per 900 feature lines, and a second still needs 4000 (twice that would be the cap, out of reach); only one lives at a time anyway, so the second marches as a Champion.

If a day has 50 or more code lines and no test or comment lines at all, a third of its Footmen (rounded down) become Berserkers, and each Berserker takes the place of two Footmen: skipping tests never makes an army stronger.

**Support is small and separate.** It does not come out of the budget:

| From | Raises |
| --- | --- |
| tests | `2·min(4, floor(√test / 5))` Wardens |
| comments | `2·min(3, floor(√comment / 5))` Archers |
| docs | `2·min(2, floor(docs / 120))` Heralds |
| config | `2·min(3, floor(config / 80))` Sappers |
| generated, vendored | nothing |

An army that would otherwise be empty gets one Footman, so the first push of the day always sends someone. A large muster marches as several platoons of at most 32 slots each, heroes first.

**Quality and veterans.** Every soldier's HP and damage are multiplied by its army's power, `quality × (1 + 0.1 × veteran rank)`: its blows are multiplied by power, and the damage it takes is divided by it. Power is recomputed from the ledger at every push, so it reaches soldiers already in the field too.

- **Veteran ranks** need both code and source files touched (the difficulty bonus counts as code here, as it does in the budget; the files must be real):

  | Rank | Code lines | Files |
  | --- | --- | --- |
  | 1 | 250 | 5 |
  | 2 | 800 | 12 |
  | 3 | 2000 | 25 |

- **Well tested.** Tests worth at least a fifth of the code (with 50+ code lines) add 5% quality. Ratios here are measured against code + 20 lines.
- **A ragged army** comes from padding:

  | Padding | Penalty |
  | --- | --- |
  | tests outweigh code 3:1 or more | up to −15% at 8:1 |
  | comments outweigh code 0.5:1 or more | up to −10% at 2:1 |
  | filler (uncounted lines such as duplicates, punctuation and tables, beyond what the push's code carries; see docs/fair-play.md) is 15% or more of the lines | up to −15% at 50% |

  Quality never drops below 0.7.

**Caps.**

- A player fields at most `min(320, floor(4000 / players)) × (1 + 0.25 × conquered)` slots (`fieldCap`: 320, or its even share of the room in a room of more than 12), and a room at most 4000 soldiers. A platoon that would break either cap waits in its capital's **muster queue** and marches when there is room. The queue holds up to 24 platoons. When it is full, a new push's soldiers fold into the waiting platoons, newest first, up to 32 slots each; any left over are not raised yet, and a later push musters them.
- An army has at most one Dragon alive. When a platoon marches out with a Dragon while one is already alive (or with two, from one squashed legendary push), each extra Dragon becomes a Champion.

**Regrouping.** Remnants fold into stronger formations of the same army. A platoon qualifies when it has 4 or fewer soldiers left, or less than 30% of its full size. It merges into the nearest platoon of its army in the field, at least as large, within 140 units, and the merged platoon is drawn up afresh, the remnant taking places in its ranks. A routed remnant of 4 or fewer that regroups at its capital joins its army's nearest such platoon at any distance.

### Army preview

`/preview` (and the shareable `/preview/{owner}/{repo}?branch=`) shows what a public repository's latest commits would raise. The page accepts `owner/repo`, `owner/repo@ref`, an SSH remote or any github.com URL of the repository (a `/tree/…` branch, a `/commit/…` sha, a file or a pull request), parsed by `rules/repoRef.ts`.

`GET /api/preview/{owner}/{repo}?branch=` reads the newest 40 commits of the branch (the default branch when none is named) and takes the newest 10 that are not merges. Each commit's diff (`GET /commits/{sha}`, at most 300 files, GitHub's omitted patches estimated from additions, exactly as ingestion reads it) goes through `measurePush` as a **standalone push on a fresh ledger**, then `armyFor` and `armyQuality`. So a row shows what that commit alone would raise as a day's first push, its difficulty bonus included: each commit's context is read against its parent for its author, exactly as ingestion reads a push's. The answer carries each commit's sha, message, author, date and link, its lines by category, files, complexity (branch points, function points, linked names) and purpose, the army as kind counts with its slot budget, quality, veteran rank and notes, and short reasons ("Army size: 101 — mostly from 1,420 lines of code (+90), plus 14 files (+2) and complexity 654 (+9)", "Complexity 182: 120 branch points, 14 new functions (+42), 9 imported names used from 4 local modules (+4.5)", "Bug fix → 2 Clerics, 2 Paladins", "1,240 generated lines raise nothing", "No tests or comments → 1 Berserker"). It also carries a **combined** army: all ten measured oldest first on one ledger, each credited to its own purpose, which is what pushing them on one day would raise. Because the ledger telescopes, its lines, size and strength equal one squashed push of the same work; only the specialists follow the messages.

- **Only public repositories.** A private or internal repository answers exactly as a missing one (404), before any of its history is read. The server's own token is used and never a viewer's; with no `GITHUB_TOKEN`, the preview reads anonymously (60 requests an hour).
- **Limits.** 10 previews a minute per address (429). An uncached preview costs up to 13 GitHub REST requests, plus 2 per repository per day for the difficulty bonus's facts and up to 10 GraphQL queries (one per commit that removes source lines; each commit's context is kept for the day). Sharing the server's token, it refuses (503) once fewer than 1,500 requests would be left for ingestion; GitHub's own rate limit also answers 503.
- **Caching.** Answers are kept per repository and branch for 5 minutes (a missing repository or branch too). Diffs are kept by sha for good, in a 48 MB LRU, so a new commit costs one diff. Repository, branch and commit-list lookups use ETags, and an unchanged answer is a free 304. The page draws each army with the battlefield's unit art (`paintPortrait`), in the viewer's latest army hue or a neutral pigment.

## 2. Hierarchy and heraldry

- **Army.** One per player per war. It has one **hue**, assigned from a colorblind-aware wheel so that players in a room are far apart.
- **Battalion.** One per repository the player pushed to today. Its flag is the army hue in a lightness and saturation step unique to the battalion, plus a **pattern** (plain, chevron, saltire, pale, fess, quarterly, bend, chief), an **emblem** (one of 12), and an accent stripe in the repository's language color. All of these are chosen from a hash of the repo name. The flag shows the repo's initials.
- **Platoon.** One per push that raises soldiers (a big push raises several). It carries its battalion's flag plus its ordinal number within the battalion (I, II, III …). It marches in column and fights in line (see *Formations* below).

### Formations

Every platoon is drawn up as one block per kind of soldier: a rectangle in ranks and files, spaced by the soldiers' size (1.9 × size + 2.5, at least 12 units). Its banner has a **form**, which the client shows:

| Form | Shape | When |
| --- | --- | --- |
| **Column** | Narrow and deep: each block at most three files and 48 units wide, the blocks one behind another down the road. Head to tail: the cavalry scouts (Outriders, Knights); the heavy foot (Berserkers, Trolls, Bone Golems, Paladins, Wardens, Footmen, Mercenaries, Skeletons); the Champion with the Heralds, Clerics and Sappers; the missile troops (Archers, Rangers, Wizards); the siege at the tail, Ballistae then Trebuchets. Griffin Riders fly in single file over the middle of the column, a Dragon over it too. | Marching |
| **Deploying** | The column halts and wheels to face the threat while each block walks to its place in the line. | An enemy banner comes within **220** of the platoon's centre (about 1.3 × a Trebuchet's 170 aggro), or a foe's walls within 200 of their edge |
| **Line** | Wide and shallow, facing the threat: Trolls, Bone Golems and Berserkers ahead; the heavy foot in the front ranks with the Champion at the centre; Paladins, Heralds, Clerics and Sappers behind the centre; the missile troops (Archers, Rangers, Wizards and Ballistae) two to three ranks back; Trebuchets behind them. Knights ride the inner wings and Outriders the outer ones. Griffin Riders hover over the middle, a Dragon behind the centre. | Deployed: after 2 seconds once the ranks are dressed and the line faces the threat, after 8 seconds at most |
| **Engaged** | The line, fighting. | Any soldier has an enemy soldier in reach |

- **The column follows its road.** The banner marches at the head and lays a trail behind it; every soldier's place is on that trail, so a column winds through gaps and around bends without anyone cutting a corner. It moves at 90% of its slowest kind's speed, siege engines and fliers aside: Trebuchets and Ballistae may trail, though a column waits for them (and for any stragglers) once its ranks fall more than 16 units behind on average. A column keeps a column's length behind the friendly column ahead on the same road.
- **Deploying.** The line forms on the column's centre of mass, so no one walks more than half the column. The formation wheels at most 0.1 radians a tick. A line is as wide as the ground allows: it is checked across the facing, and where rock or water is closer, blocks grow deeper, rows that do not fit fall in behind, the cavalry rides behind the foot, and the line shifts sideways to sit between the obstacles. It re-checks the ground every 2 seconds. Friendly lines on the same ground side-step until they stand side by side.
- **The line advances or holds.** A line facing an enemy army advances on its banner at 60% of the column's pace until the two banners are 45 apart and the front ranks meet. A line facing walls presses on toward its objective at 85% pace. A platoon that reaches its objective draws up in line to hold it.
- **Back to column.** A deployed platoon re-forms in column only when no threat has been within **275** (1.25 × the deploy radius) for 5 seconds, so it never flip-flops at the edge.
- **Re-forming.** A platoon is drawn up afresh when it changes between column and line, comes out of a fight, takes in a regrouped remnant, regroups after a rout, or (every 2 seconds, never mid-fight) loses soldiers. Each kind's soldiers keep their order front to back and left to right, so survivors step up into the gaps and the ranks close.

### Two layers of the AI

**The platoon** (strategic) gets its objective from the war council (section 4) and plans its road to it over a **hex map** of the battlefield: hexes 52 units apart; a hex is passable if its centre is open ground, and a step between neighbours only if the straight line between their centres stays on open ground; a step into forest costs 17, into the open 10. The route is an A* search with a fixed tie-break (lowest f, then h, then hex id), cached per start and goal hex, and replanned only when the objective changes or the banner is stuck for 8 ticks. A banner stuck for 20 ticks follows the map's flow field for a while instead. The route still to march is part of the platoon's state, so a client can draw it.

**The soldier** (tactical) fights for itself once its platoon has deployed, within the platoon's engagement zone: within its banner's leash (1.7 × its aggro range) and within reach of its own place in the line (52 units for line infantry, 64 for brutes, 84 for a Champion, 160 for cavalry, range + 16 for missile troops). It drops a foe that strays further, and with no foe it returns to its place.

| Role | Kinds | Picks |
| --- | --- | --- |
| Line infantry | Footmen, Wardens, Mercenaries, Skeletons, Berserkers, Sappers | The nearest foe in front of it, the ones it beats preferred. A foe already beset by 2 + size ÷ 4 attackers is left alone unless it is at arm's reach, so attackers spread along the enemy line. |
| Brutes | Trolls, Bone Golems | Foes near the enemy's banner: they push the centre. |
| Champion | Champion | The enemy's best: a foe's renown value weighs heavily. |
| Missile troops | Archers, Rangers, Wizards, Trebuchets, Ballistae, Dragon | Foes in range, the wounded and the valuable first; a Ballista the biggest and most valuable (a Dragon, a Troll, a Champion before any footman). They hold their rank, step back from melee, and do not advance beyond their place. |
| Cavalry | Knights, Outriders, Griffin Riders | Missile troops, casters, Clerics, Heralds and Sappers first. A rider in front of a deployed enemy line swings wide round its flank before turning in. |
| Healers | Clerics, Heralds, Paladins | They stay behind the front tending the wounded and strike only at foes that come within 24 (44 for a Paladin); a Cleric smites any foe within its reach of 55, picking as missile troops do. |

Sappers still run for the walls of their objective once within their leash, and Trebuchets prefer walls (only walls that can be stormed now; otherwise they hold and shoot at soldiers). A soldier below 20% of its HP steps back a rank, trading places with a fresh soldier (above 60%) of its kind behind it, and then fights only what reaches it.

**Under fire.** A platoon remembers the last enemy soldier whose missile struck it and the last tower that did, with the tick (`hitBy`, `hitAt`, `towerBy`, `towerAt`; part of its state and the checksum). For 8 seconds after a hit:

- **A shooter it can reach** (within 320 of its banner, and not sheltering inside a tower's reach of walls it may not storm) is its threat: the line wheels toward the shooter itself (not its banner) and advances on it at a column's pace, whatever its objective. Riders ride it down, missile troops shoot back once it is in range, and line soldiers within their aggro range close on it (up to its attacker cap), even beyond their usual leash and place in the line.
- **Fire it cannot answer**, from a tower on walls it may not storm (see *Keep-out rings*, section 3) or from a shooter sheltering under them, sends it back out of reach: a line backs away still facing the walls, a column turns and marches off, nobody waiting for stragglers, until its soldiers' centre is beyond the keep-out ring plus half its depth (or beyond the shooter's range).


## 3. The battlefield: a ring of capitals

### The map

The capitals stand evenly spaced on a **ring**, one per seat, slot 0 at the top and slots climbing clockwise. The ring's radius is `max(440, 700 × slots / 2π)`, so neighbouring capitals are about 700 units apart along it however many seats there are; the map is a disc reaching 230 beyond the ring.

- **The centre** is impassable: a great lake (two maps in three) or a mountain massif, with a ragged shore 160 inside the ring. No army cuts across; every road runs around the ring. Fliers still fly over it.
- **The front road.** The ring itself is kept clear as a road. Between each pair of neighbouring capitals, at the road's midpoint, stands a **border fort** (site `slots + s` lies between capital `s` and capital `s + 1`). It pays 2 renown a minute while held and is where neighbours meet.
- **Terrain.** Forests, rocks and pools are painted in the band either side of the road from seeded noise in one sector and rotated into the others, so every seat sees the same map. Forest slows ground movement by 40% and halves missile damage; water and rock are impassable.

**Seats.** A war is generated with `slots = clamp(seats + 1, 3, 16)`, where *seats* counts members and sparring bots, leaving a spare seat for someone who joins during the day. Seats are handed out in a seeded shuffle of the slots drawn from the war's seed (`seatOrder`), so who neighbours whom changes every day; a late joiner takes the next free seat in that order. A spare seat is open ground: the front road simply runs past it, with both its forts on that front. Sparring bots fill every war to at least 3 seats.

### Fronts

The **ring of owners** is the claimed capitals in clockwise order, each with the player who holds it. A player's capitals form runs around it; each run has a **front** at either end, toward the nearest other owner clockwise and counter-clockwise. A player's **neighbours** are the owners its fronts face. Normally that is two; with two owners left they share both fronts; with one, the war is won. (A realm split by a rising's retake has a pair of fronts for each piece.) The ring is recomputed every tick from who holds which capital, so it is never stored, and every client derives the same one.

Soldiers fight only **foes**: their neighbours, a rising at the gates of a capital they hold, and anyone who counts them as such. Everyone else passes by unharmed, and towers, fireballs and dragon fire spare them too.

### Capitals and sieges

- **Capital.** It has walls and a tower (20 damage, reach 160 plus half the walls' radius, a volley every 4 s of one bolt, and one more for every 8 foes within reach, up to 24). Its walls are `12000 + 75 × slots` HP (150 a slot when armies were half the size, so a siege takes as long as it did), where *slots* is the army its holder's work has raised today, so a busy player's walls need a bigger storming party. **Walls come down no faster than over 30 minutes of siege** (1/48 of the war), however many strike them (at most `maxHp / 9000` a tick in a day-long war), and slower still while the siege pace ramps up (see below): at full pace a full capital holds out for half an hour, a captured one (at half its walls) for a quarter of an hour, and the tower bleeds the besiegers all the while, so a siege is a stand that the defender, its other neighbour and every push can still turn. Masons restore 10 HP a second while no siege is on; a capital is **besieged** while its holder's foes stand at the walls, and the siege lifts 30 seconds after the last of them leaves.
- **Home turf.** Within 220 units of any capital they hold, a player's soldiers take 20% less damage.
- **When walls can be stormed.** The siege timetable is paced by the war's length *D* (its `ticks`, from its start to its reset), so a short war (a new room's first, a test day, the demo) runs the same course as a full day, only faster. In a day-long war:
  - **The sieges open at 40% of the war** (09:36): no walls can be breached before; the morning is for the border forts.
  - **The siege pace ramps up.** From then, the most a capital's walls can lose a tick is its full-pace share (`maxHp / (D/48)`) times a ramp that grows from 0 when the sieges open, as the square of the time since, to 1 at **70% of the war** (16:48). Armies at the walls strike far harder than that, so the ramp, not the wall HP, sets the pace: a full capital besieged without a break from the moment the sieges open falls no sooner than about 58% of the way through the war (14:00 of a day), and a siege laid later, or broken and laid again, falls at the pace of its hour. First captures spread over the afternoon by how soon an army holds the walls, instead of landing all at one minute.
  - **Barred gates.** A founder's gates stay barred, besides, until 8% of the war (about 2 hours) after its first push of the day, or until 65% of the war (15:36), whichever comes first, so no one is conquered in their sleep. A capital that has changed hands is never barred.

  | War length | Sieges open | Earliest fall | All gates open | Full pace | Grace after a first push | Breach at full pace |
  | --- | --- | --- | --- | --- | --- | --- |
  | 24 h | 9 h 36 m | about 14 h | 15 h 36 m | 16 h 48 m | 1 h 55 m | 30 m |
  | 6 h | 2 h 24 m | about 3 h 30 m | 3 h 54 m | 4 h 12 m | 29 m | 7.5 m |
  | 3 h (the demo) | 1 h 12 m | about 1 h 45 m | 1 h 57 m | 2 h 6 m | 14 m | 3.75 m |

- **The approach.** An army can storm a foe's walls only while it holds the border fort beside them on its front (a rising: either fort beside its lost home). Every siege begins with a field battle for the fort, and the war council masses its army there before it storms: it sends platoons at the walls only once `10 + 15 × (walls HP / full walls)` of its soldiers have gathered on the front (a platoon alone holds the fort and waits for the others).
- **Keep-out rings.** A tower reaches `160 + walls radius / 2` (195 for a capital). A platoon keeps its banner out of the *keep-out ring*, the tower's reach plus a margin of 45 (240), of every foe's walls except the ones it has been sent to storm and may storm now: its line does not advance, drift after a melee or side-step into it, its soldiers do not go after foes sheltering within the tower's own reach, and foes there are no threat to march on. Waiting therefore happens where the tower cannot reach: at the border forts (every fort stands at least 60 beyond every keep-out ring, at any ring size) or, for a rising, on the road just outside the ring. A Trebuchet (range 175, measured to the walls' face) outranges the tower only from inside the keep-out ring, so it bombards walls only during a siege. A platoon at a fort it holds with nothing near faces down the road toward the foe's walls.

### Capture

A capital at 0 HP is **captured** by the player who struck the last blow:

- It changes hands, its walls stand again at half of its new holder's full walls, and it is the new holder's **muster gate** from then on.
- The captor gains renown: 120 for the first capture of that capital today, then `120 / n` (rounded down) for the n-th.
- The garrison inside the walls is cut down, and the loser's platoons within 220 of the walls break and fall back to the nearest capital it still holds.
- **Production.** Every capital a player holds beyond its own home multiplies its army's budget and its field cap by another 25% (`1 + 0.25 × conquered`). The bonus counts toward the target army, so the next push musters the difference for the whole day's ledger, splitting and squashing stay equal, and the telescoping muster works as before. A player that loses a captured capital keeps the soldiers it raised; it musters again only once its ledger is worth more than it has.

**Muster gates.** Each capital has a gate on the road either side of it. A new platoon is assigned a front (the one under the most pressure for the strength already sent there, so quiet fronts alternate) and marches out of the gate of its player's capital at that end of its realm, along the road.

### Risings

A player who loses its last capital is not out. It keeps its ledger and keeps pushing; its musters appear as a **rising**: platoons flagged `rising` that gather on the ring road just outside the keep-out ring of its lost home's walls (240 along the road), take the forts beside it, and storm the walls to retake it. A rising is a foe only of whoever holds its home. Retaking the home makes the player a ring owner again, with its fronts recomputed. A player with no capital who has raised soldiers today is still in the war (`stillIn`).

### Victory

When one player holds every claimed capital (risings in the field do not count), the war is **won**: a `victory` event, and the field stands still from that tick. The server concludes the war at once (the digest and lifetime records are written as at a reset) and the room stays locked on the finished war, refusing pushes and joins, until its reset, when the next war begins as usual. If the reset comes first, the winner is the player holding the most capitals, then the one with the largest share of the day's code (its *contribution*: the code lines its ledger counts, after the knee), then the most renown, then the one who joined first (`compareStandings`; the HUD's standings and the digest use the same order).

### Border forts

A border fort flips after a single army has held it uncontested for 10 seconds. Progress drains back while the fort is contested or empty.

## 4. No manual control: the war council

**No manual control: your code is your only command.** A player's armies answer only to the work they push and to their **war council**, the same AI for everyone. No player gives orders of any kind: the only inputs to the simulation are players joining and their pushes. The server answers an old client that still sends a manual command with `410 Gone` and records nothing, and replays of older wars that hold manual commands are read with them skipped.

Each player's **war council** runs every 3 seconds. It gives each platoon an objective on its front: the front in its direction nearest it (a rising's: the march on its lost home). The candidates are the front's border forts, the foe's capital at its far end, the player's own capital at this end, every capital it holds, and any fort between two of its own capitals. It weighs:

- the objective's renown and kind (forts to take or hold; a foe's walls once the approach is won and enough soldiers have massed (50 for full-strength walls, down to 20 for breached ones: twice the 25 and 10 of armies half the size, so a siege waits for the same share of an army); its own walls, urgently, while they are under siege)
- distance (supply lines)
- enemy and friendly strength nearby

Platoons already sent somewhere make that site less attractive to the next. Routing on the hex roads (section 2) runs around the ring band.

## 5. Morale and routs

Every platoon has morale from 0 to 100. Morale falls by `150 / platoonSize` per soldier lost and drains (2 per second) while the platoon is engaged and outnumbered 2 to 1 within 90 units. A Herald halves both. Morale recovers slowly out of combat. A platoon with a living Champion or Dragon never drops below 1.

At 0 morale the platoon **routs**: it stops fighting and flees to the nearest capital its player holds (a rising's, to the fort beside its lost home). There it regroups at 60 morale and takes a new objective from its war council. Routs make fights end and stay readable.

## 6. Winning the day, and renown

**The ring is the prize.** A player who holds every capital wins the war on the spot (section 3, *Victory*). If the reset comes first, the winner is the player holding the most capitals, then the largest share of the day's code, then the most renown, then the one who joined first (nobody wins a day no one fought: no renown and no capital taken). The standings show each player's lines counted today beside its army.

**Renown is the running score**, the last tiebreak (after capitals and the day's code) and the race the HUD shows:

| Source | Renown |
| --- | --- |
| Border fort held | 2 per minute |
| Kill | the victim's value: 1 for Footmen, Archers, Sappers and Skeletons; 2 for Wardens, Heralds, Outriders, Mercenaries and Berserkers; 3 for Rangers and Clerics; 4 for Knights and Bone Golems; 5 for Paladins, Wizards, Trebuchets, Ballistae and Griffin Riders; 6 for a Troll; 10 for a Champion; 30 for a Dragon |
| Capturing a capital | 120 for the first capture of that capital today, then `120 / n` for the n-th |

A fort pays in full only while its owner has soldiers near it; an ungarrisoned fort pays a quarter of its renown, rounded down. Nothing singles out the leader: there is no bounty on the leader's soldiers and its capital draws no one more than any other. The ring itself makes the leader face only its two neighbours.

## 7. The daily digest

When a war ends, the server computes a digest from the final world and the war's inputs. The function is pure and deterministic. The digest contains:

- the winner, the final standings, and the renown each player gained
- the code each player pushed, by category
- superlatives, so most active players earn one:

| Award | Goes to |
| --- | --- |

Members may switch on **Rest** for a UTC day, which keeps their streak without growing it. A room owner may set a Slack or Discord incoming-webhook URL (https only, those hosts only), and the digest is posted there, with up to 3 tries on a network error, 429 or 5xx.

## 8. Rooms

- **Visibility.** A public room appears in the lobby. Anyone can watch it, and any signed-in player can join. A private room is reachable only through its invite link. Only members and holders of the link can watch it.
- **Settings.** The owner sets the room's name, its reset hour (in UTC), and how many sparring bots it has (0–6). Bots push synthetic code so that a room is never empty, and a war always has at least three seats: bots beyond the setting fill a smaller ring.
- **The demo** (`/demo`) runs a three-hour sparring war of five bots entirely in the browser (bots there push every few minutes, all day), so at 16× its sieges open after about 4½ minutes, the first capital can fall after about 6½, and the war is often won before its 11 minutes are out. The demo and replays have a **Playback speed** control at the foot of the screen; it only changes how fast the recorded or simulated war plays, and live rooms have none.
- **Bots keep office hours.** Each bot draws its day afresh from the war's seed (`botDay`): a working window of 7 to 10 hours starting between 08:00 and 10:00 room-local time (hours since the room's reset), a push rate drawn log-uniformly from 0.8 to 6 an hour (the range of real developers), and on two days in five an evening session of 30 to 90 minutes between 19:00 and 23:00. Outside these a bot does not push, so a lone human is not out-pushed around the clock. Each persona's pushes are scaled (`volume`) to carry about as much code as a typical developer's, some 150 lines: its style decides what its army is made of, not how much it is worth. A short test day (`DAY_MINUTES`) compresses the same schedule into its length.
- **Owner tools.** The owner can rename the room, change its settings, remove members, and rotate the invite code.
- **In the room.** Viewers see presence (who is watching). Signed-in viewers can send **cheers**, and members can use a short chat (240 characters, 6 messages per 10 seconds). Cheers are just for show: a **Cheer** button at the foot of the chronicle and chat opens a small palette of labelled reactions (*Huzzah!*, *What a fight!*, *Well held!*, *Nice shot!*, *On fire!*, *All hail!*, *Gasp!*, *Ouch!*), and each floats over the sender's capital and up the screen with its word and the sender's name. They change nothing on the field. Chat and cheers are not part of the replay.
- **Rollover.** At the reset the war is run to its last tick, its digest and lifetime records are written in one transaction, and the next war starts where the last one ended (or at the latest reset boundary, if the server was down past it). Every viewer gets the new war's hello at once. If any step fails, the war stays active and the whole rollover is retried.
- **A war won early.** When one player takes the whole ring, the server stops stepping it at the tick it was won, finishes it the same way (digest and lifetime records in one transaction; viewers get a `war` message with the digest ready), and keeps the finished war live, locked to pushes and joins, until the reset; then the next war starts at the reset boundary as usual. A restart in between finds the room standing on its finished war.

## 9. Determinism and replay

The simulation is pure. It uses only `+ - * / Math.sqrt Math.floor Math.abs Math.min Math.max` (its few sines and cosines come from a series of those, `dmath.ts`), a seeded PRNG stored in the world, and iteration over arrays in index order. Derived data (flow fields, the hex map and its cached routes) is rebuilt identically from the map. It runs at 5 ticks per second.

A war's **replay** is everything needed to rebuild it, and nothing more:

```json
{
  "v": 1,
  "seed": 123, "slots": 6, "members": 4, "tickMs": 200,
  "startsAt": 1761177600000, "endsAt": 1761264000000,
  "players": [{ "login": "ana", "id": 1, "hue": 210, "slot": 0, "bot": false }],
  "repos": [["ana/parser", "TypeScript"]],
  "inputs": [[0, "join", 0, 0, 210], [1200, "push", 0, 0, [120, 30, 12, 4, 0, 18, 0, 0, 9], 3, "fix: tokenizer", 4, 17, 0, 2], [3000, "doc", 0, 2]]
}
```

The war's length is part of its header: `endsAt - startsAt` over `tickMs` is the world's `params.ticks`, which paces its sieges (section 3), so a replay, a recovered war and a spectator's client all agree on it (a snapshot carries `params`, and the checksum covers the length). `repos` holds `[name, language]` pairs. A join's `slot` is the seat the server drew from the war's seeded shuffle. A push input is `[tick, "push", p, repo, lines, commits, message, files, branches, churn, filler, functions, links, bonus?]`; its lines, files, branches, function points, links and difficulty bonus are signed changes to the player's ledger (rows recorded before complexity was parsed end at `filler`, and replay with none; the bonus is written only when nonzero, so rows without one, old or new, end at `links`). The bonus is measured at ingestion from GitHub's blame and recorded, so a replay never fetches context. The map, the capitals and everything else derive from `seed`, `slots` and `members`. The chronicle (history log) is a pure function of the simulation's events, so a replay reproduces it too. The server keeps a snapshot every 10 minutes only to seek quickly, thins older ones to one an hour, and 14 days after a war ends keeps only its final one. They are a cache, not a source of truth.

## 10. Architecture

```
GitHub events/compare ─▶ ingest ─▶ SQLite (users, pushes, seen commits)
                                   │
              rules (pure) ────────┴─▶ push input ─▶ war (per room) ─▶ sim (pure, 5 Hz)
                                                       │
                                  inputs + snapshots ──┼─▶ SQLite
                                                       └─▶ WebSocket ─▶ clients run the same sim
```

- **One authoritative Node process.** It runs every room's war, the poller, HTTP and WebSockets. The scheduler steps the wars every 200 ms in slices of about 8 ms, yielding to sockets and HTTP between them, so a request waits about one slice however many rooms are busy (a room of 16 fighting with ~3,000 soldiers costs about 5 ms a tick, so one core can step some 40 such rooms flat out, about 20 at half load; per soldier the cost is what it was when rooms held half as many). Measuring a push is split in two (`rules/ledger.ts`): `preparePush` reads, classifies and parses the diff (tree-sitter: about 70 ms for a typical commit, about 0.7 s for the largest of this repository's last 81) in a pool of worker threads (`server/parsePool.ts`, `PARSE_WORKERS`, 2 by default), and `applyPush` moves the SQLite ledger on the main thread inside the push's transaction (milliseconds). The worker's result is plain data and gives exactly what measuring inline gives; a worker that fails or takes over 30 s falls back to parsing inline. Blame processing for the difficulty bonus is light (a pass over the ranges) and stays on the main thread. A field with no soldiers costs microseconds a tick. A room nobody watches still simulates every tick exactly (outcomes never depend on spectators); it only skips the checksums sent to viewers.
- **Derived data.** Flow fields are built per site the first time one is needed, and a restored world shares the map (and every cache derived from it) with recent worlds of the same seed, so a resync or a recovered war does not rebuild them.
- **Lockstep spectators.** A client receives one snapshot (the *hello*), then only inputs stamped one second ahead, and simulates locally with interpolation. A checksum every 10 seconds catches divergence. It covers the units, platoons (their formations, routes, trails, fronts, rising flags and the last shooter and tower to strike them included), structures (holders, walls and sieges), shots and sites, the victor, and each player's renown, ledger, raised army, capitals and feats, so a divergence in the books shows before the next push would reveal it.
- **Hello limits.** A hello carries a full snapshot, so the hub rations them per viewer (the user, or the address for anonymous viewers) across all their sockets: a burst of 8, then one per second. A socket asks to resync at most every 2 seconds; extra asks are folded into one deferred hello rather than dropped. When 4 of a viewer's sockets are already waiting, a new one is turned away with close code `1013` (try again later), and the client backs off and retries, and a socket more than 4 MB behind is dropped. A new war's hello goes to everyone at once.
- **Client connection.** Reconnects back off from 1 s, doubling to 30 s, with up to 50% jitter so a server restart is not met by every viewer at once; only a session that went live resets the backoff. A watchdog reconnects after 45 seconds without any message, or when a resync is not answered within 10 seconds.
- **Hidden and background tabs.** A hidden tab draws nothing and simulates nothing; after 30 seconds hidden it lets its socket go. Shown again, it reconnects for a fresh snapshot, and a tab that comes back (or wakes) more than 25 ticks behind asks for one rather than replaying the gap. Catching up never takes more than about 8 ms of simulation per frame. A visible but unfocused window draws at 30 fps.
- **What a platoon is doing, and why.** `sim/stance.ts` derives, as a pure function of the world (so it adds nothing to the snapshot), each platoon's reason: *Marching*, *Fighting* (with the kind of shooter it is going after), *Waiting for sieges* (with the time left), *Gates barred* (time left), *Massing* (`n` of `m` soldiers on the front), *Need the fort first*, *Holding the fort*, *Under fire, pulling back*, *Regrouping* (back at the colours after a rout), *Rising*, *Besieging* (when the walls could fall at the siege's pace) or *Routing*. The client refreshes it a few times a second and shows it four ways:
  - **Commander barks.** A small vellum speech scroll with a tail over a platoon's banner, lettered in italic ink, carries a line in its commander's voice ("Three hours till the rams may roll…", "We need more swords — 24 of 50.", "Trebuchet! Ride it down!"). Several lines per state; which one is a hash of the platoon and how many times it has spoken. A platoon speaks when its state changes, then every 45 to 90 seconds (staggered by platoon; none on first sight), at most four on screen, the selected platoon first (it may take a lesser bark's place), then the followed one, then the viewer's own, then those on screen; off-screen platoons never speak, and far out only the selected one does. Barks fade in and out (they pop under reduced motion) and give way to other map labels through the label layer's collision.
  - **On the chart** (mid zoom and closer): a waiting or massing platoon pitches a camp behind its flank (two tents, a campfire whose glow joins the light pass, a stack of spears) and wears a vellum tag on its banner with an hourglass while it waits on the siege clock and its muster count ("38/50"); an army at a fort it holds plants its standard at the fort's edge and sets pickets round its side; a besieging platoon draws a dashed siege line in its pigment to the walls (the siege camp and the wall ring with its breach estimate stand there already); a platoon pulling back trails chevrons the way it withdraws.
  - **The state scroll.** The selected platoon, and the one under the pointer, carry a scroll under their ranks naming the state ("Besieging @grace-bot", "Massing 24/50", "Waiting · sieges in 1h 12m") and whose platoon it is.
  - **The Inspector** gives the full sentence: "Massing at the Ember Fort — 38 of 50 soldiers; sieges open in 32 minutes."
- **Client presentation.** The sun follows the war's simulated tick, not the wall clock, so a replay, a catch-up or a waking tab shows the hour being watched. Sound is off on every visit until the viewer opts in; sampled cues ship as Ogg Vorbis and AAC, and audio fades and suspends while the tab is hidden.
- **Levels of detail.** Far out (zoom below 0.5, back above 0.6, cross-faded) no soldier is drawn: each platoon shows its kind-blocks, rectangles in its army's colour sized by headcount, ink-outlined, with the kind's woodcut glyph, so a column reads as a chain of bars and a line as wide ones, its banner token at the centre and a clash mark where engaged platoons meet. The frame's cost then follows platoons, not soldiers. At mid zoom soldiers away from the centre of the view stop their walk cycle and minor sparks are thinned; close up everything is drawn.
- **Off the main thread.** The chart's pixel layers and the unit art (on an OffscreenCanvas) are computed in workers while the page starts, and a replay seek runs the simulation in a worker and hands back the world it reached. Each has a main-thread fallback. The live simulation stays on the main thread: one step every 200 ms costs a few milliseconds even in a large war.
- **Loading.** The front page and the live room ship in the first bundle; the digest, replay, history, profile, Hall, Season, Armory and army preview load on first visit, and fonts load without blocking the first paint.
- **Service worker.** It serves hashed assets from its cache and the app shell, sprites, audio and fonts stale-while-revalidate; the API, sign-in, webhooks and the WebSocket are never cached. Every build carries the version of its simulation and protocol: the page checks it against the server's (`/api/version`, and the hello), and a page from another build purges the cache and reloads, so an old build never sticks after a deploy that changed the checksums. `SERVICE_WORKER=0` is the kill switch: pages unregister it and the server serves a worker that removes itself; `?nosw` does the same for one browser.
- **SQLite in WAL mode.** Every input is written to the log before it is broadcast. On restart, a war loads its latest snapshot, replays the logged inputs, and catches up to wall-clock time.
- **Retention.** Pruned every 6 hours:

  | Data | Kept |
  | --- | --- |
  | ledger balances | count for 7 days after they last moved; deleted after 8 |
  | seen commits and push records | 14 days |
  | chat | 30 days |
  | snapshots of ended wars | the final one only, after 14 days |
- **Stack.** TypeScript everywhere. Fastify and `@fastify/websocket` on the server. PixiJS 8 renders the battlefield and React the HUD. Vite builds the client, and Vitest runs the tests.
- **Parsing (server only).** `rules/complexity.ts` reads complexity with `web-tree-sitter` (WebAssembly, pinned) and the grammars' published `.wasm` files, **vendored** in `assets/grammars/` (JavaScript, TypeScript and TSX, Python, Go, Rust, Java, Kotlin, Ruby). `scripts/vendor-grammars.ts` (`pnpm grammars`) fetches each pinned grammar package with `npm pack` (no install scripts run), extracts its `.wasm` and license, and records package, version and sha256 in `assets/grammars/grammars.json`; a test checks the files against it. The grammar packages are not dependencies: they carry native bindings with install scripts, and the Kotlin one pulls in `npm-check-updates` at runtime. `pnpm.onlyBuiltDependencies` allows install scripts for `better-sqlite3` and `esbuild` only. A grammar loads the first time a push needs it, in the parse worker, and the runtime is imported dynamically, so nothing of it reaches the client bundle; neither does any git code. Each distinct line's branch count is cached (up to 200,000 lines).
